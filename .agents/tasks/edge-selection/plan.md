## Design decisions (each with rationale)

1. Selection state lives in `CanvasSurface` as `selectedItemId: string | null`, separate from `selectedUserId`. Rationale: same ownership as hover/focus; no new store; resets follow the same adjust-during-render pattern the lint config requires (no reset inside `useEffect`).
2. Nodes are NOT restyled by producing new node objects. `scene.nodes` stays the identical array (so the fit effect, `getNodes()` and RF internals see no change); cards read selection through a new `SelectionContext` (selectedId, lineage node-id Set, stable-per-selection `toggle`). Rationale: guarantees "no layout, no node move, no refit" like hover, and keeps node data pure. Selection changes re-render the ~10 to 60 cards (acceptable; selection is a click, not a pointermove); hover stays on the separate cheap `EmphasisContext`.
3. Edges ARE restyled (new array via a memo) by a new pure `highlightEdges(edges, selectedId, emphasisId)` that composes with `emphasizeEdges` by reusing exported fragments (`raiseEdge`, `dimEdge`, `incomingStatusEdge`), not by copying them. With no selection it returns exactly `emphasizeEdges(edges, emphasisId)`, so today's behavior and tests are untouched.
4. Selection click goes through React Flow's `onNodeClick` (same place grid drill-in lives), keyboard through the card's `onKeyDown`, pane clear through `onPaneClick`. The card gets NO `onClick` (would double toggle). `elementsSelectable={false}` (decision: nothing depends on it; leaving it on yields a second `.selected` visual and edge-click selection).
5. Edge color for the selected path = the SELECTED ITEM's incoming status edge `data.reviewStatus` (already the aggregated status for mixed items), mapped through an exhaustive `STATUS_STROKE: Record<AccessReviewStatus, string>` of the same four `--vc-*` vars the scene uses. A unit test pins it against the scene's own stroke so the two cannot drift.
6. Selected-card treatment: a second, offset outer ring in `--ink` (neutral, not one of the four status colors, flips in dark mode) separated from the status ring by a `--canvas` gap: `box-shadow: 0 0 0 2px var(--vc-graph-status), 0 0 0 5px var(--canvas), 0 0 0 7px var(--ink), var(--shadow)`. Status ring, stripe and corner icon stay.
7. Associated edges: the item's incoming user to item edge plus every edge forward-reachable from the item over the VISIBLE scene edges (so reference hidden gives only the first edge; toggling reference updates automatically because the highlight is derived from `scene.edges`). Upstream parent to item reference edges (an entitlement that is also nested under another held item) are NOT associated. To include upstream later it is a one-line change: in `lineageEdgeIds` also seed `edges.filter(e => e.target === itemId && isReference(e))`. Document this in the module header.
8. Accessibility add-on: a `role="button"` card replaces the card's children semantics, so the corner status icon would no longer be exposed to assistive tech. Fix: give the status `<svg>` an optional `id` prop (via `useId` in `AccessNode`) and set `aria-describedby` on the card to it, so "Role: Role A, button, not pressed, Needs review" is announced. Names stay `${Kind}: ${label}`.
9. Hover while an item is selected: hovering/focusing a DIFFERENT first-level item raises its incoming status edge (preview, undimmed, class `vc-graph-edge-emphasized`) while the selected path stays highlighted; hovering/focusing the selected item adds nothing; reference nodes add nothing.
10. Pane-click focus caveat: if clicking the empty pane leaves browser focus on the previously clicked card, the focus-emphasis would keep that card's edge raised and dim the rest, looking like a stuck selection. Browser step S6 checks `document.activeElement`; if a card stays focused, blur it inside `onPaneClick` (only when the active element is inside `.vc-graph-wrap`). Do not add this unless the browser shows the problem.
