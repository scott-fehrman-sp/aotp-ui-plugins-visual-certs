## Design decisions (each with rationale)

D1. Emphasis state is a pair of tiny React states in `CanvasSurface` (`hoverId`, `focusId`), fed by cards through a React context whose value is a stable object of the two setters. Rationale: the pure scene builder must not see hover, cards sit inside React Flow's node renderer so a context is the only non-prop channel, and a stable context value means hovering re-renders only `CanvasSurface` (restyle of edges) and never every card. `emphasisId = hoverId ?? focusId` so pointer wins and a keyboard-focused card stays emphasized after the pointer leaves another card.

D2. `emphasizeEdges(edges, focusedNodeId)` is a pure helper in a new `src/graph/emphasizeEdges.ts`, applied in a `useMemo` keyed on `[scene.edges, emphasisId, inDrilldown]` and fed to `<ReactFlow edges>`. It returns the SAME array reference when there is nothing to emphasize (null id, or id has no incoming status edge, i.e. a reference node or the user), so those cases are provably a no-op. The fit effect, scene memo and layout never read hover state.

D3. (Gap in the brief, assumption made.) The brief says to aim the long-list viewport at "the top of the lane" with "user node + first items in view". Those cannot both hold: the preserved layouts center the user on the lane midpoint (the user is ~1,400 scene px, ~900 screen px at 0.65, below the top of a 25-item lane, and the canvas is only 490-640 px tall). Rule chosen, implemented as one generic per-axis function: when content overflows an axis, ALIGN THE CONTENT START to the start of the overlay-free region if the focus box (the user card) is fully visible in that aligned window; otherwise CENTER THE USER in the free region. Consequences: the rank axis (user at the min edge) is start-aligned, so the user column is at the left (LR) / top (TB) of the free region; the cross axis (user at lane midpoint, long lane) centers the user so the user plus the nearest items on both sides are on screen, and the reviewer scrolls up and down for the rest. For a lane short enough to put the user inside the top-aligned window the result IS the literal top of the lane. The report must state this explicitly so the user can say if they truly want the lane top with the user off-screen. Layout is NOT changed.

D4. (Gap in the brief, assumption made.) "Fit zoom below READABLE_MIN_ZOOM triggers the readable path" taken literally would also trigger for the standard fixture (measured shown 0.644 at 1700x1000, 0.404 at 1000x700; hidden 0.492 at 1000x700), contradicting Z2 ("short graph unchanged"). Two constants therefore: `READABLE_MIN_ZOOM = 0.65` is the zoom USED in the readable path (tune with screenshots; card label 15 px * 0.65 = 9.75 px); `SCROLL_MODE_FIT_ZOOM = 0.3` is the trigger: only when the fit-everything zoom is below 0.3 (measured dense: 0.15 to 0.238, i.e. every long case) is the graph treated as a long list. Graphs fitting at >= 0.3 keep today's overlay-aware `fitView` byte-for-byte. The report states both values, why, and that the trigger is tunable.

D5. Overlay assignment in the readable path avoids spending the scarce SCROLL axis. A 25-item lane scrolls vertically (LR) or horizontally (TB). With today's strip model the minimap lands in a full-width bottom strip (162 px of 490-640) and Back in a top strip, leaving ~262 px (1000x700) of free height, about 3 items. `computeFitPadding` gains an optional `scrollAxis: 'x' | 'y'` plus `scrollAxisPenalty` (default 3): when choosing the side for an overlay, thicknesses on the scroll axis are multiplied by the penalty for the COMPARISON only (the padding applied is still the real thickness). Back, legend, minimap, Controls, toolbar then go to left/right strips for LR, leaving the full height (minus base margins) for scrolling. Without `scrollAxis` the function is bit-for-bit unchanged (existing tests stay valid). A top-center panel (the "no expanded access" note) still chooses the top because the left/right strips would be enormous.

D6. The scroll hint is a polite `role="status"` pill in a `Panel position="top-center"` with `pointer-events: none` so wheel/drag pass through it. It is shown when BOTH (a) the latest fit plan for the current `fitKey` was the readable path (state `{fitKey, long, itemCount}` set from the rAF in `FitOnSceneChange`; keyed on `fitKey` so a stale plan never shows) AND (b) a store selector says the scene bounds are not wholly inside the canvas at the current transform (boolean selector, so no re-render per pan frame). (b) hides it after the Controls fit-view button shows everything. The panel carries class `vc-graph-fit-ignore` and `measureOverlays` skips it (otherwise a top-center pill would be charged as a huge side strip on later refits). The pill's rect lies inside the strip band already reserved by the Back panel (same top offset, same height), so it never needs its own padding; verify visually.

D7. Fit-view control: the `Controls` fit button keeps calling `fitView()` with React Flow defaults (padding 0.1, minZoom 0.15), which shows the whole graph and is independent of the readable rule. Only add `fitViewOptions` to `Controls` if the browser run shows otherwise.

D8. If the raised edge is NOT painted over cards in the real browser (React Flow renders edge groups and the node layer as separate stacking contexts), fallback: draw the single emphasized edge as an extra path in `ViewportPortal` (renders above nodes) using `getBezierPath` from the two node boxes, and keep the in-place edge only for dimming. Decide ONLY from the real-browser pixel check (see H1-paint), never from reading source.

## Revised invariant (replaces "no node intersects an overlay after fit; every node inside the canvas" for long graphs)

Mode A: fit zoom >= `SCROLL_MODE_FIT_ZOOM` (0.3). The OLD strict rules apply unchanged: no node rect intersects any `.react-flow__panel` overlay by more than 0.5 px; every node rect inside the canvas (1 px tolerance).
Mode B: fit zoom < 0.3 (long graph). After auto-fit:
 (i) zoom equals `READABLE_MIN_ZOOM` (+/- 0.005);
 (ii) the user card and the 3 nearest lane items (>= 3, or all if fewer) are fully inside the overlay-free region, clear of every overlay;
 (iii) every node rect that lies wholly inside the free region is clear of every overlay (true by construction; asserted);
 (iv) nodes outside the canvas, or cut by the canvas edge or the free-region boundary, are ALLOWED (reached by scrolling) and are counted and reported, not failed. A card scrolled partly under the hint pill, minimap or a strip is scroll-state, reported with counts;
 (v) the last item can be scrolled fully into the canvas clear of overlays (wheel; shift+wheel in TB); first item likewise.
The hint pill itself must not intersect the toolbar, Back, legend, minimap or Controls in any scenario.
Document this in the doc comment of `FitOnSceneChange` and `planFit`.
