## Design decisions (final, do not re-decide)

1. Single-lane layout is an explicit builder option, not a different function. Signature becomes `buildAccessScene(graph, rankdir, options: AccessSceneOptions = {})` with `export interface AccessSceneOptions { singleLane?: boolean }`. Rationale: the canvas already drives hide/show from one `showReference` boolean, a boolean option keeps the builder pure and deterministic, and omitted options must reproduce today's output exactly. The canvas passes `{ singleLane: !showReference }`. `singleLane` is documented as "the graph contains only the user and its first-level items (the output of `withoutReference`)". It is not the builder's job to filter.
2. Lane assignment in single-lane mode: `user` nodes are rank 0; every other node is rank 1 (one lane), at rank coordinate `MARGIN + 1 * bandStep`, the same coordinate the role column has in shown mode. Skip dagre entirely in this mode (no cross-axis information from dagre is used). Share the node/edge mapping code with lanes mode so styling, handles, `zIndex`, `data` and edge output stay identical.
3. Ordering in the lane: `kindRank` ascending (role < accessProfile < entitlement; reusing `kindRank` is the same order, with `source` after entitlement if one ever slips in), then `label` via `a.label.toLowerCase().localeCompare(b.label.toLowerCase(), 'en')`, then `id` via plain `<` / `>` comparison (locale-independent, so it is deterministic everywhere). Rationale: grouping by kind keeps a reviewer's mental model (roles first), label order makes it scannable, id breaks ties.
4. Spacing and centering in the lane reuse the existing arithmetic: stride `crossExtent + NODE_SEP` (64+48 in LR, 200+48 in TB), `spanStart = -((n - 1) * stride) / 2`, top-left cross coordinate `spanStart + index * stride`. The user (rank 0 lane, normally one node, placed with the same formula) therefore sits at cross coordinate 0, which is the lane midpoint because all cards have the same extent.
5. Shown mode stays byte-for-byte unchanged. The lanes path must keep its current arithmetic. A golden test (item 1) captured BEFORE touching the builder guards this.
6. Fit becomes overlay-aware with per-side pixel padding (the approach in the brief), computed by a pure helper from measured overlay rectangles. Strip model: each overlay is assigned to exactly ONE side of the canvas, the side where it needs the smallest strip thickness; that side's padding grows to cover it plus a clearance gap. Because each overlay lies fully inside its assigned strip and `fitView` keeps the node bounds inside the padded area, no node can touch any overlay. Rationale: it is simple, provable, deterministic and unit-testable. Tradeoff accepted: a corner overlay costs a full-width/height strip, so the graph may be smaller at small sizes (explicitly allowed). A global search over side assignments would use space slightly better but is not worth the complexity. Overlays are discovered generically as every `.react-flow__panel` descendant of React Flow's root DOM node with non-zero size (covers toolbar, Back, legend, Controls, MiniMap only when mounted, note only when rendered, attribution). Nothing to maintain when a panel is added.
7. Refit triggers: the existing `sceneKey` plus minimap visibility, plus canvas width/height from the React Flow store (window resize). Minimap toggle currently does not refit, and must, otherwise showing the minimap can cover nodes.
8. Do NOT change `.vc-graph-wrap` height by default. Padding already guarantees no overlap regardless of height. The coder measures the resulting zoom at 1000x700 and reports it. Only if the standard fixture ends up pinned at `minZoom` (0.15) and overlapping because of it would a height change be justified; if so change `AccessGraph.css` only and state why in the commit body.
9. Defect A in SHOWN mode with a dense graph is MEASURED AND REPORTED, not fixed (item 8). The `zIndex` rule that cards sit above edges stays: raising edges above cards would strike lines through card names, which the user previously objected to. Mitigation is proposed in the report, not implemented.

- [ ] 4. Add the pure fit-padding helper (Defects B and C, math part).
      Create `WT/src/graph/fitPadding.ts` (pure, no React, no DOM, no mutation of inputs):
        - `export interface Box { left: number; top: number; right: number; bottom: number }` (coordinates relative to the canvas top-left);
        - `export interface FitPadding { top: number; right: number; bottom: number; left: number }`;
        - `export function computeFitPadding(canvas: { width: number; height: number }, overlays: readonly Box[], options?: { base?: number; gap?: number; maxFraction?: number }): FitPadding`. Defaults: `base = 24` (minimum margin on every side), `gap = 12` (clearance between an overlay and the graph), `maxFraction = 0.75`. Algorithm: ignore overlays with non-positive width/height; for each overlay compute strip thickness per side: top = `box.bottom`, right = `canvas.width - box.left`, bottom = `canvas.height - box.top`, left = `box.right` (clamped at 0); choose the side with the smallest thickness, ties broken in the fixed order top, right, bottom, left; set `padding[side] = max(padding[side], thickness + gap)`; start every side at `base`. Finally cap: if `top + bottom > maxFraction * height` (or `left + right > maxFraction * width`) scale both sides of that axis down proportionally so the sum equals the cap (graph always keeps at least 25% of each axis; in that degenerate case overlap is possible and that is accepted). Round each value up with `Math.ceil`.
        - `export function toFitViewPadding(p: FitPadding)` returning `{ top: '${p.top}px', right: ..., bottom: ..., left: ... }` (typed as the React Flow `Padding` object form; import the type from `@xyflow/react` if it is exported, otherwise declare a local structural type).
